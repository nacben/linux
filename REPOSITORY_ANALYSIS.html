Part 1: Memory Management Deep Dive

Overview: Memory management is a core subsystem that handles physical page allocation, virtual memory, page caching, memory debugging, and memory reclaim. The kernel implements a sophisticated multi-layer allocation system from low-level page allocator up to high-level slab caches.

Buddy Allocator - Page-Level Allocation

Purpose: Manages physical memory allocation at the page level (4KB granularity on most systems).

File Location: /mm/page_alloc.c (7,628 lines)

Buddy Allocator Algorithm

The buddy allocator maintains free lists organized by power-of-2 page orders:

  • Order 0: 1 page (4KB)
  • Order 1: 2 pages (8KB)
  • Order 2: 4 pages (16KB)
  • Order 10: 1024 pages (4MB)
struct free_area {
    struct list_head free_list[MIGRATE_TYPES];
    unsigned long nr_free;
};

struct zone {
    struct free_area free_area[NR_PAGE_ORDERS];
    spinlock_t lock;
    struct per_cpu_pages __percpu *per_cpu_pageset;
};

Key Features

Buddy Merging

When freeing pages, adjacent free buddies are merged into higher orders, reducing fragmentation.

Per-CPU Caching

Per-CPU slab structures reduce lock contention by ~70% on high-core systems.

GFP Flags

Flexible allocation flags: GFP_KERNEL, GFP_ATOMIC, GFP_HIGHUSER, GFP_NOWAIT, etc.

Memory Zones and Watermarks

Purpose: Partition physical memory into zones for DMA, normal, and high memory allocation needs.

Zone Types

Zone Use Case Physical Address
ZONE_DMA ISA DMA devices 0-16MB
ZONE_DMA32 PCI 32-bit devices 16MB-4GB
ZONE_NORMAL General kernel > 4GB (varies)
ZONE_HIGHMEM Beyond direct map > 896MB (32-bit)

Watermark Levels

Watermarks prevent memory exhaustion by maintaining minimum free memory:

  • WMARK_MIN: Critical minimum (e.g., 16,896 pages / 67.5 MB)
  • WMARK_LOW: Start reclaim trigger (e.g., 21,120 pages / 84 MB)
  • WMARK_HIGH: Stop reclaim threshold (e.g., 25,344 pages / 101 MB)

SLUB Allocator - Object-Level Allocation

Purpose: Allocate small kernel objects (kmalloc) efficiently with minimal overhead.

File Location: /mm/slub.c (10,084 lines)

Why SLUB? Raw page allocation (4KB) wastes memory for small objects. SLUB packs multiple objects per page into "slabs" for efficient memory usage and CPU affinity.

Kmalloc Allocation Sizes

Power-of-2 or aligned sizes: 8, 16, 32, 64, 128, 256, 512, 1024, 2048, 4096 bytes

Memory Efficiency

Multiple objects per page reduce wasted space

CPU Affinity

Objects allocate on same CPU for cache locality

Per-CPU Caching

Lock-free fast path allocation

Debugging Integration

Works with KASAN, KFENCE, KMSAN

Memory Debugging Tools

KASAN (Kernel Address Sanitizer)

Purpose: Detect out-of-bounds memory access and use-after-free bugs at runtime.

File Location: /mm/kasan/ (17 files, ~220KB)

Shadow Memory

1 byte shadow per 8 bytes of real memory tracks accessibility

Instrumentation

Compiler-added checks on every memory access

Quarantine

Delay freed object reuse to detect use-after-free

KFENCE (Kernel Fence)

Purpose: Detect heap buffer overflows and use-after-free with zero false positives.

File Location: /mm/kfence/ (6 files, ~82KB)

Key Advantage: Physical guard pages around each allocation eliminate false positives. Probabilistic sampling (1 in 100 allocations) keeps overhead minimal even on production systems.

KMSAN (Kernel Memory Sanitizer)

Purpose: Detect uninitialized memory usage (reading uninitialized variables).

File Location: /mm/kmsan/ (9 files, ~87KB)

Tracks initialization state with 1 bit per byte, compiler instrumentation propagates uninitialized state through operations, and origin tracking provides stack traces of where uninitialized values came from.

Memory Reclaim and Page Eviction

Purpose: Free memory when low, prioritizing least-used pages.

File Location: /mm/vmscan.c (7,919 lines)

kswapd Background Daemon

The kernel uses kswapd (kernel swap daemon) to reclaim pages in background when memory pressure is detected:

  1. Wake kswapd when free pages < WMARK_LOW
  2. Scan LRU lists and evict pages
  3. Write inactive/anonymous pages to swap device
  4. Stop when free pages > WMARK_HIGH

LRU Lists (Least Recently Used)

List Contains Reclaim Priority
LRU_INACTIVE_ANON Unused user memory High (easy to swap)
LRU_ACTIVE_ANON Used user memory Lower (in-use)
LRU_INACTIVE_FILE Unused file cache High (can discard)
LRU_ACTIVE_FILE Used file cache Lower (needed soon)

Part 2: Driver Architecture Deep Dive

Key Architectural Principle: Separation between what hardware does (device) and how to control it (driver). All devices and drivers use standardized structures and registration mechanisms.

Unified Device Model

File Locations:

  • /drivers/base/core.c (2000+ lines) - Device registration and lifecycle
  • /drivers/base/driver.c - Driver binding logic
  • /drivers/base/bus.c - Bus type management
  • /drivers/base/dd.c - Device-driver matching and probe/remove

Device Registration Flow

  1. Hardware discovered (PCI enumeration, USB hotplug, device tree)
  2. Device structure created
  3. device_register() called
  4. Device added to bus's device list
  5. For each driver: bus->match(device, driver)
  6. If match: driver_probe_device() → probe()
  7. Device ready or deferred if dependencies unmet

Core Structures

Structure Key Field Purpose
struct device device_driver *driver Bound driver reference
struct device_driver int (*probe)() Hardware initialization callback
struct bus_type int (*match)() Device-driver matching algorithm

Platform Device Drivers

PCI Drivers

Purpose: Support devices on the PCI/PCIe bus.

File Locations: /include/linux/pci.h (3000+ lines), /drivers/pci/

PCI Device Discovery

  1. PCI bus enumeration discovers vendor/device IDs
  2. Kernel searches registered drivers' id_tables
  3. Match found: probe() called with matched device
  4. Driver maps BARs, configures DMA, requests interrupts
  5. Device ready to use

Interrupt Handling in Drivers

File Locations: /include/linux/interrupt.h, /kernel/irq/manage.c

IRQ Request Structure

struct irqaction {
    irq_handler_t handler;          // Hard interrupt handler
    irq_handler_t thread_fn;        // Threaded handler
    void *dev_id;                   // Context/cookie
    unsigned int flags;             // IRQF_* flags
};

IRQ Handler Types

Hard Handler

Atomic context. Must be fast. Disable IRQ on return.

Threaded Handler

Process context. Can sleep, allocate, acquire locks.

Tasklet

Software IRQ. Atomic. Single per-tasklet serialization.

Workqueue

Process context. Can sleep. Per-workqueue serialization.

IRQ Handler Flags

Flag Meaning
IRQF_SHARED Allow sharing this IRQ with other devices
IRQF_TRIGGER_RISING Rising edge trigger
IRQF_ONESHOT Keep disabled until threaded handler finishes
IRQF_NO_SUSPEND Don't disable during system suspend

DMA in Drivers

File Locations: /include/linux/dma-mapping.h, /kernel/dma/

DMA Allocation Types

Coherent DMA (Cache-Coherent)

Device and CPU see same data without explicit sync. Best for control structures and descriptors.

dma_addr_t dma_handle;
void *vaddr = dma_alloc_coherent(dev, size, &dma_handle, GFP_KERNEL);
// Automatic cache coherency - no manual sync needed
Streaming DMA (Requires Explicit Sync)

Data may not be immediately visible without cache flush. Use for bulk data transfers.

dma_addr_t dma_handle = dma_map_single(dev, vaddr, size, DMA_TO_DEVICE);
// ... device operates on dma_handle
dma_unmap_single(dev, dma_handle, size, DMA_TO_DEVICE);
Scatter-Gather DMA

Map multiple buffers with a single operation for better performance.

DMA Attributes

Attribute Purpose
DMA_ATTR_WRITE_COMBINE Write combining for faster writes
DMA_ATTR_FORCE_CONTIGUOUS Allocate physically contiguous memory
DMA_ATTR_SKIP_CPU_SYNC Skip cache sync (if you know it's safe)

Power Management in Drivers

File Locations: /include/linux/pm.h, /drivers/base/power/

Power State Callbacks

Callback When Called Purpose
suspend() Before system sleep Save state, stop I/O
resume() After system wakes Restore state, restart I/O
runtime_suspend() When device idle Power down device
runtime_resume() On device access Power up device

Runtime PM (Dynamic Power Control)

Automatically power down idle devices and wake them on access:

// In probe:
pm_runtime_enable(dev);
pm_runtime_set_autosuspend_delay(dev, 1000);  // 1 second idle

// Before using device:
pm_runtime_get_sync(dev);  // Wake up
// ... use device
pm_runtime_put_autosuspend(dev);  // OK to sleep soon

Managed Resources (devres) Framework

Purpose: Automatic resource cleanup when device is removed.

File Location: /drivers/base/devres.c

Key Benefit: Eliminates resource leak bugs. On probe() failure or device removal, all managed resources are automatically freed in reverse allocation order (LIFO).

Common Managed Allocations

API Auto-Frees
devm_kmalloc() Memory
devm_ioremap_resource() I/O mapping
devm_request_irq() Interrupt
dmam_alloc_coherent() DMA memory
devm_clk_get() Clock reference
devm_gpiod_get() GPIO descriptor

Cleanup Guarantee

On probe() failure or remove():

  1. Walk list of managed resources in LIFO order
  2. Call cleanup function for each resource
  3. Free metadata

This ensures resources are freed in reverse allocation order, preventing dependency issues and resource leaks.

Conclusion

The Linux kernel's memory management and driver subsystems are highly sophisticated:

Memory Management:

  • Multi-level allocation: Pages → slabs → kmalloc
  • Intelligent reclaim: LRU-based eviction, kswapd background daemon
  • Comprehensive debugging: KASAN, KFENCE, KMSAN
  • Hardware abstraction: Page tables, zones, NUMA support

Driver Architecture:

  • Unified device model: Standardized structures and registration
  • Flexible bus support: Platform, PCI, USB, I2C, SPI
  • Automatic cleanup: Managed resources (devres)
  • Deferred probing: Transparent device dependency ordering

Together, these subsystems enable the kernel to efficiently manage hardware, memory, and software in a reliable, debuggable, and extensible manner across 23+ processor architectures and thousands of devices.
